# Maestro Twin — SI-02: Production Line Digital Twin & Bottleneck Intelligence

## Problem

Manufacturing lines consist of interconnected stages. A delay or capacity
limit at one stage propagates through the rest of the line and reduces
overall throughput. The challenge: build a digital-twin prototype that
ingests operational data and identifies bottlenecks, downtime propagation,
throughput losses, resource utilization, and operational inefficiencies —
and use it as a **decision and simulation system**, not just a picture of a
factory.

## Proposed solution

**Maestro Twin** is a discrete-event digital twin that treats the production
line as a decision system: every screen answers a specific operational
question with a number backed by a confidence interval, not a static
visualization.

### The core idea

One simulation engine, fed by *any* data source. Most digital-twin demos
hardcode their model to one factory's data. We separated the two concerns
completely:

```
Any data source → normalize → map → canonical Plant model → ONE engine → answers
```

Whether the input is a manually-built template, an uploaded CSV with
arbitrary column names, a plain-English description, or a live MQTT/REST
feed, it all converges on the same canonical `Plant` object before the
engine ever sees it. The engine itself contains zero source-specific logic —
enforced by an automated test that inspects its source code.

### How it addresses each requirement

| Requirement | Approach |
|---|---|
| **Bottlenecks** | Shifting-bottleneck detection across the shift, not just a single static constraint |
| **Downtime propagation** | Live and simulated views trace how a failure at one stage cascades — upstream *blocked*, downstream *starved* — tagging each hop as directly **observed** from the data source or **inferred** from serial topology |
| **Throughput losses** | A loss waterfall decomposes total loss into starvation, blocking, failures, changeover, and yield |
| **Resource utilization** | Per-stage/per-machine utilization from the same simulation run |
| **Operational inefficiencies** | Automated inefficiency flags plus a ranked advisor: which single change is worth making first |
| **What-if simulation** | Patch any parameter (capacity, cycle time, failure rate); common-random-number variance reduction gives a clean before/after with a confidence interval, so "would this actually help" has a statistically honest answer |
| **"Decision system, not visualization"** | Every output is a number to act on (add a machine here, expect +X units/h ± Y) — never just a colored diagram |

### The data layer (what makes it universal, not just a demo)

1. **Normalize** — a deterministic parser reads CSV/JSON/XLSX, resolves
   column-name aliasing ("Work Centre" = "asset_id" = "machine"), converts
   units and timestamp formats, and produces a data-quality report (missing
   fields, bad timestamps, unknown states, duplicates).
2. **Map** — machines are grouped into ordered serial stages via an explicit
   stage column, naming patterns, or first-appearance order — each with a
   confidence score and a plain-English reason, fully editable before
   commit. Data implying branching or merging is *flagged*, never silently
   flattened, since the engine is honestly serial-only.
3. **Estimate** — cycle time, MTBF, and MTTR are derived from observed event
   logs where there's enough evidence; thin evidence falls back to reference
   values and says so.
4. **Live** — a connector abstraction (replay / file / REST / SQL / MQTT)
   feeds a live twin that tracks per-machine state with a bounded event
   ledger, entirely separate from the simulation twin, so running a what-if
   never touches live state.

Every value carries a provenance tag: **observed → estimated → reference →
calibrated**. Nothing is ever presented as more certain than it actually is —
including an AI-assisted layer (Gemini) that may only suggest column
mappings or draft an estimated starting model from a description; it never
performs the simulation, statistics, or bottleneck math itself, and every
suggestion is deterministically validated before use.

### Honesty as a design constraint

Where we didn't have the real MDFS interface spec and captured session, we
didn't invent one. The MDFS connector ships fully built but reports itself
`UNCONFIGURED` and falls back to a synthetic replay generated by the real
engine — clearly labeled `REPLAY`, never presented as live. We treat that as
a feature of the solution's credibility, not a gap to hide.

## Run it (30 seconds, no install)

```bash
cd maestro-twin
python3 run.py
```

Requires Python 3.10+. **No `pip install`, no network access, no API key
needed.** A browser tab opens automatically at `http://127.0.0.1:8000`.

```bash
python3 run.py --check       # run the full automated test suite instead
python3 run.py --port 9000   # use a different port
```

Optional, to enable Gemini-assisted mapping / description / narration:
```bash
export GEMINI_API_KEY=...          # everything works without this too
```

## Demo path

1. **Pick a reference line** on the launch screen (or **+ Create New Factory**
   to upload `tests/fixtures/greenfield_line.csv` — a fixture with different
   column names/units than any template, proving the pipeline is universal).
2. **Diagnose tab** — bottleneck, downtime propagation, loss waterfall.
3. **What-if tab** — patch a parameter (e.g. add a machine at the constraint),
   compare against the baseline with a confidence interval, watch the
   bottleneck migrate.
4. **Live tab** — press *Start engine replay* to watch machine states change
   in real time, with a propagation readout that tags each effect
   `observed` vs `inferred`.
5. **Advisor tab** — ranked interventions with the same statistical rigor.

## Architecture

```
connector (file / REST / SQL / MQTT-MDFS / replay)
        │  → canonical Event → LiveTwin (observed state, bounded ledger)
        │
upload/description → normalize → map → estimate → Plant (canonical model)
                                                        │
                                                        ▼
                              dtwin/engine.py  (DES: blocking, failures,
                              dtwin/analysis.py  changeover, yield — untouched)
                              dtwin/whatif.py    (CRN what-ifs + CIs)
```

`dtwin/engine.py`, `analysis.py` and `whatif.py` contain **no source-specific
logic** and import nothing from the ingestion or connector layers — enforced
by an automated test that checks their imports and source text. One engine,
any data source.

| **Connectors**: Replay, File, REST (polling), SQL (read-only sqlite3, single `SELECT`), MDFS (MQTT-first) | New, tested |
| **Normalizer**: CSV/JSON/XLSX, alias tables, unit/timestamp/state conversion, data-quality report | New, tested |
| **Mapper**: groups machines into ordered serial stages, confidence + reason per stage, editable | New, tested |
| **Anomaly detection** on the live stream (downtime, cycle drift, throughput, repeat failures, queue buildup) | New, tested |
| **Gemini integration** (mapping suggestions, description → estimated model, narration) — validated, never does math | New, tested |
| **"+ Create New Factory" wizard** and **Data Sources** view | New |

11 ingestion = **58 tests, all passing** (`python3 run.py --check`).

`observed` (from real data, enough samples) · `estimated` (derived, or from
Gemini) · `reference` (industry benchmark fallback) · `calibrated` (fit against
an observed shift).

## Why it's a decision system, not a dashboard

Every screen answers a specific question with a number you can act on:
*where* is the constraint, *how far* does a failure propagate and to whom,
*what* does adding a machine actually buy you (with a confidence interval, not
a point estimate), and *which* of several possible interventions is worth
doing first. Nothing is rendered as more certain than the data backing it.
